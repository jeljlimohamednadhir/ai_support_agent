Documentation AI Support Agent

Bienvenue dans la documentation complète d'AI Support Agent, l'assistant intelligent pour diagnostiquer, analyser et résoudre les problèmes techniques en temps réel.

📚 Version actuelle
Cette documentation correspond à la version 1.0.0 d'AI Support Agent.

Qu'est-ce qu'AI Support Agent ?

AI Support Agent est une plateforme complète qui combine l'intelligence artificielle, le traitement du langage naturel et l'analyse de code pour automatiser le support technique.

Fonctionnalités principales

  • Collecte automatique : Ingestion de logs, introspection DB, clonage Git
  • Analyse intelligente : Workers asynchrones pour parser et enrichir les données
  • Knowledge Graph : Stockage structuré dans Neo4j et Qdrant
  • RAG Pipeline : Recherche sémantique et génération de réponses contextualisées
  • Validation continue : Feedback loop avec experts humains
  • Observabilité : Dashboards et métriques en temps réel

Cas d'usage

  • Support technique niveau 1 et 2
  • Diagnostic automatique d'erreurs
  • Documentation automatique de code legacy
  • Onboarding de nouveaux développeurs
  • Analyse d'incidents et post-mortems

🏗️ Architecture

AI Support Agent suit une architecture microservices moderne et scalable.

Composants principaux

Composant Technologie Rôle
Frontend React + TypeScript + Vite Interface utilisateur responsive
Backend API FastAPI (Python) API REST avec validation Pydantic
Workers Celery + Redis Tâches asynchrones (parsing, ETL)
PostgreSQL Postgres 15 Métadonnées et données relationnelles
Neo4j Neo4j 5 Knowledge Graph (relations)
Qdrant Qdrant Vector Store (embeddings)
Redis Redis 7 Cache + Message Broker

Flux de données

  1. Ingestion : Le Collector récupère les données (Git, logs, DB)
  2. Traitement : Les Workers analysent et enrichissent les données
  3. Indexation : Stockage dans Neo4j (graphe) et Qdrant (vectors)
  4. Requête : Le Chatbot utilise RAG pour générer des réponses
  5. Validation : Les experts valident et corrigent les réponses

📦 Module Collector

Le Collector est responsable de l'ingestion des données depuis différentes sources.

Sources supportées

  • Git : Clone et analyse des repositories
  • Logs : Parsing de fichiers logs (text, JSON, structured)
  • Base de données : Introspection de schémas SQL
  • API : Découverte d'endpoints REST/GraphQL

Utilisation via UI

  1. Accéder à l'onglet "Collecte"
  2. Sélectionner le type de source
  3. Fournir les credentials/URL
  4. Lancer la collecte
  5. Suivre la progression en temps réel

Utilisation via API

POST /api/v1/collector/git

Clone et analyse un repository Git

Body

{
  "repo_url": "https://github.com/user/repo",
  "branch": "main",
  "credentials": {
    "username": "user",
    "token": "ghp_xxx"
  }
}

Réponse

{
  "task_id": "abc-123",
  "status": "pending",
  "message": "Collection started"
}

⚙️ Workers

Les workers Celery traitent les tâches asynchrones en arrière-plan.

Types de workers

  • code_analyzer : Parsing AST, extraction de métadonnées
  • log_analyzer : Parsing et enrichissement de logs
  • db_analyzer : Analyse de schémas et relations
  • doc_analyzer : Extraction de documentation

Monitoring des workers

# Vérifier les workers actifs
celery -A celery_app inspect active

# Statistiques
celery -A celery_app inspect stats

# Flower (UI web)
celery -A celery_app flower
💡 Scalabilité
Vous pouvez lancer plusieurs instances de workers pour augmenter le débit : celery -A celery_app worker --concurrency=8

🧠 Knowledge Graph

Le Knowledge Graph stocke les relations entre entités dans Neo4j.

Types de nœuds

Type Description Propriétés
File Fichier source path, language, size
Function Fonction ou méthode name, signature, docstring
Class Classe ou interface name, type, members
Endpoint Route API method, path, params
Table Table DB name, columns, indexes

Types de relations

  • CONTAINS : File → Function/Class
  • CALLS : Function → Function
  • INHERITS : Class → Class
  • USES : Endpoint → Table
  • REFERENCES : Function → Table

Requêtes Cypher

// Trouver toutes les fonctions appelées par une fonction
MATCH (f:Function {name: "process_data"})-[:CALLS]->(called)
RETURN called.name

// Trouver les tables utilisées par un endpoint
MATCH (e:Endpoint {path: "/api/users"})-[:USES]->(t:Table)
RETURN t.name

💬 Chatbot

Le chatbot utilise un pipeline RAG pour fournir des réponses contextualisées.

Pipeline RAG

  1. Embedding : La question est convertie en vecteur
  2. Recherche sémantique : Top-K documents pertinents via Qdrant
  3. Re-ranking : Score de pertinence affiné
  4. Construction du prompt : Template avec contexte injecté
  5. Génération : LLM génère la réponse
  6. Post-processing : Formatage et extraction d'actions

API Chatbot

POST /api/v1/chat/query

Envoie une question au chatbot

Body

{
  "query": "Comment résoudre l'erreur 'connection timeout' ?",
  "context": {
    "project_id": "proj-123",
    "user_id": "user-456"
  },
  "options": {
    "top_k": 5,
    "temperature": 0.7
  }
}

Réponse

{
  "response": "L'erreur 'connection timeout' peut être causée par...",
  "sources": [
    {"id": "doc-1", "title": "Guide de troubleshooting", "score": 0.92},
    {"id": "doc-2", "title": "Configuration réseau", "score": 0.87}
  ],
  "suggested_actions": [
    "Vérifier la configuration du firewall",
    "Augmenter le timeout dans app.config"
  ]
}

Personnalisation

Modifiez backend/app/services/chatbot/chatbot_service.py pour :

  • Changer le modèle LLM
  • Ajuster les prompts système
  • Modifier la stratégie de re-ranking
  • Ajouter des post-processors custom

✅ Validation

Le module de validation permet aux experts de reviewer et corriger les réponses du chatbot.

Workflow de validation

  1. Le chatbot génère une réponse
  2. La réponse est marquée "En attente de validation"
  3. Un expert review la réponse
  4. L'expert peut : Valider / Corriger / Rejeter
  5. Les corrections sont persistées et utilisées pour fine-tuning

Métriques de qualité

  • Taux de validation : % de réponses validées sans correction
  • Score BLEU : Similarité avec réponses de référence
  • Temps de réponse : Latence moyenne P50/P95/P99
  • Satisfaction utilisateur : 👍 / 👎

🔐 Authentification API

Toutes les routes API (sauf /health) nécessitent une authentification JWT.

Obtenir un token

POST /api/v1/auth/login 
{
  "username": "admin",
  "password": "password"
}

Réponse

{
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "token_type": "bearer",
  "expires_in": 1800
}

Utiliser le token

Incluez le token dans le header Authorization de toutes vos requêtes :

Authorization: Bearer eyJhbGciOiJIUzI1NiIs...

📊 Monitoring

Métriques clés

  • API : Latence P50/P95/P99, taux d'erreur, throughput
  • Workers : Queue depth, tâches/sec, erreurs
  • Base de données : Connexions actives, query time, cache hit rate
  • LLM : Tokens/sec, coût, latence

Stack Prometheus + Grafana

# Lancer Prometheus + Grafana
docker-compose -f docker-compose.monitoring.yml up -d

# Accéder à Grafana
open http://localhost:3001

Alertes

Configurez des alertes dans infrastructure/prometheus/alerts.yml :

  • Latence API > 2s
  • Taux d'erreur > 5%
  • Worker queue depth > 1000
  • Espace disque < 10%

🔒 Sécurité

Best practices implémentées

  • ✅ Authentification JWT avec refresh tokens
  • ✅ HTTPS obligatoire en production
  • ✅ Rate limiting (100 req/min par IP)
  • ✅ Validation stricte des inputs (Pydantic)

  • ✅ CORS configuré par whitelist
  • ✅ Headers de sécurité (CSP, X-Frame-Options, etc.)
  • ✅ Secrets stockés dans des vaults

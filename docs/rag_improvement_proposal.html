0 Analyse de la défaillance observée

Scénario exact

Un ingénieur N3 a travaillé avec le chatbot pour analyser un ticket BRASIL. Le chatbot a correctement identifié et proposé une procédure de résolution. Après résolution, l'ingénieur a demandé :

"Génère le message de clôture pour le dépositaire. La cause racine : le fichier d'entrée du script ne respectait pas le masque de nommage requis par le script 'Extraction Mode BRASIL spécial ORRAHD'."

Au lieu de générer un message de clôture basé sur cette cause confirmée, le chatbot a produit un nouveau diagnostic sans rapport, mentionnant :

  • Compteurs de ressources logiques
  • VP / VLAN
  • Table t_d_controlable_rscs
  • Systèmes SEBA, 42C (non mentionnés dans le ticket)

Cartographie des 5 défaillances

#DéfaillanceComposant fautif dans le code actuelGravité
F1 Perte de contexte — La cause racine confirmée est ignorée au tour suivant _build_context_summary() : extraction regex insuffisante pour capturer "cause racine confirmée". extract_prior_procedure_from_history() : ne capture que les procedure_id, pas les causes racines textuelles. Critique
F2 Mélange de contextes — RAG récupère des incidents non liés (SEBA, 42C, VLAN) orchestrator.process() : absence de filtre sur le domaine applicatif et le type d'incident lors de la recherche vectorielle. Aucun tag de domaine dans les embeddings. Critique
F3 Hallucination de systèmes — Introduction de systèmes (SEBA, 42C) non mentionnés ANTI_HALLUCINATION_RULES : les règles existent mais ne sont pas vérifiées après génération LLM (pas de post-génération guard). Le LLM "contamine" la réponse depuis des blocs RAG non filtrés. Critique
F4 Mode conversationnel incorrect — Phase de clôture traitée comme phase de diagnostic diagnostic_behavior.py : _CONTEXTUAL_INTENTS inclut ticket_closing mais le routage de phase conversationnelle n'est pas structuré en machine à états. Aucun mécanisme forçant le maintien de la phase. Majeur
F5 Ton trop mécanique — Réponse robotique même en phase de clôture depositor-facing format_diagnostic_response() : format unique pour toutes les audiences. Pas de détection d'audience ni adaptation du registre de langue. Mineur
Diagnostic de fond : Le chatbot traite chaque message comme une nouvelle requête indépendante. L'état conversationnel (phase, cause racine, audience cible) n'est pas persisté entre les tours. Le RAG ignore l'isolation de domaine et injecte des blocs potentiellement non pertinents dans le prompt LLM.

1 Gestionnaire d'état conversationnel (Conversation State Manager)

1.1 Problème architectural

Le service actuel reconstrulit le contexte à chaque tour via _build_context_summary() (extraction regex de ~20 tokens). Il n'existe pas de machine à états explicite qui trace la phase courante de la conversation. Le résultat : le LLM peut ignorer que l'incident est résolu et relancer un diagnostic.

1.2 Modèle de machine à états proposé

Les 4 phases de la conversation de support :

DIAGNOSTIC → INVESTIGATION → RESOLUTION → CLOSING

PhaseDéclencheurs d'entréeDéclencheurs de sortieComportement LLM attendu
DIAGNOSTIC Premier message · description d'erreur · code d'exception · log Utilisateur confirme une hypothèse OU demande les étapes Recherche RAG active · slot-filling · propose des hypothèses de cause
INVESTIGATION Ingénieur dit "j'ai vérifié", "les logs montrent", "j'ai trouvé" Utilisateur confirme la cause racine Affiner le diagnostic · corréler avec KB · ne pas proposer de nouvelles hypothèses
RESOLUTION Ingénieur dit "procédure", "comment résoudre", "quelle est la FR" Utilisateur dit "c'est résolu", "ticket fermé", "message de clôture" Fournir les étapes de résolution · se baser sur la cause racine verrouillée
CLOSING "message de clôture", "fermer le ticket", "informer le dépositaire", "génère le message" Nouvelle conversation / nouveau ticket Aucune recherche RAG · utiliser uniquement l'historique + cause racine · adapter le ton au dépositaire

1.3 Structure de données de l'état conversationnel

# Nouveau dataclass à ajouter dans diagnostic_behavior.py

from dataclasses import dataclass, field
from enum import Enum
from typing import Optional, List, Dict

class ConversationPhase(str, Enum):
    DIAGNOSTIC    = "diagnostic"
    INVESTIGATION = "investigation"
    RESOLUTION    = "resolution"
    CLOSING       = "closing"

@dataclass
class ConversationState:
    phase: ConversationPhase = ConversationPhase.DIAGNOSTIC
    application: str = ""
    incident_summary: str = ""
    confirmed_root_cause: Optional[str] = None      # verrouillé une fois confirmé
    confirmed_procedure_id: Optional[str] = None    # procédure appliquée
    resolution_confirmed: bool = False
    audience: str = "n3_engineer"                   # "n3_engineer" | "colleague" | "depositor"
    locked_systems: List[str] = field(default_factory=list)   # systèmes mentionnés dans le ticket
    excluded_systems: List[str] = field(default_factory=list) # à exclure du RAG
    turn_count: int = 0

1.4 Détecteur de transition de phase

# Patterns de transition à intégrer dans chatbot_service.py

_PHASE_TRANSITIONS = {
    ConversationPhase.DIAGNOSTIC: {
        # → INVESTIGATION
        "investigation": re.compile(
            r"\b(j'ai\s+v[eé]rifi[eé]|les\s+logs\s+montrent|j'ai\s+trouv[eé]|"
            r"j'ai\s+constat[eé]|en\s+regardant|apr[eè]s\s+v[eé]rification|"
            r"la\s+cause\s+semble|le\s+probl[eè]me\s+vient\s+de|j'ai\s+identifi[eé])\b",
            re.IGNORECASE,
        ),
    },
    ConversationPhase.INVESTIGATION: {
        # → RESOLUTION
        "resolution": re.compile(
            r"\b(comment\s+(r[eé]soudre|corriger|proc[eé]der)|quelle\s+(est\s+la\s+)?proc[eé]dure|"
            r"quelles?\s+(sont\s+les\s+)?[eé]tapes|FR\s+pour|appliquer\s+la\s+proc[eé]dure|"
            r"que\s+faire\s+maintenant|que\s+dois[- ]je\s+faire)\b",
            re.IGNORECASE,
        ),
    },
    ConversationPhase.RESOLUTION: {
        # → CLOSING
        "closing": re.compile(
            r"\b(message\s+de\s+cl[oô]ture|fermer\s+le\s+ticket|cl[oô]turer|"
            r"informer\s+le\s+d[eé]positaire|[eé]crire\s+au\s+d[eé]positaire|"
            r"g[eé]n[eè]re\s+le\s+message|ticket\s+r[eé]solu|c'est\s+r[eé]solu|"
            r"probl[eè]me\s+r[eé]gl[eé]|r[eé]solution\s+confirm[eé]e|"
            r"informer|notifier|communiquer\s+(la\s+)?r[eé]solution)\b",
            re.IGNORECASE,
        ),
    },
}

def detect_phase_transition(
    current_phase: ConversationPhase,
    message: str,
) -> Optional[ConversationPhase]:
    """Retourne la nouvelle phase si une transition est détectée, sinon None."""
    transitions = _PHASE_TRANSITIONS.get(current_phase, {})
    # Closing override : peut être déclenché depuis n'importe quelle phase
    _CLOSING_PATTERN = _PHASE_TRANSITIONS.get(ConversationPhase.RESOLUTION, {}).get("closing")
    if _CLOSING_PATTERN and _CLOSING_PATTERN.search(message):
        return ConversationPhase.CLOSING
    for target_phase_name, pattern in transitions.items():
        if pattern.search(message):
            return ConversationPhase[target_phase_name.upper()]
    return None

1.5 Intégration dans chatbot_service.py

La méthode process_message() doit :

  1. Reconstruire ConversationState à partir de l'historique (sérialisation JSON dans les métadonnées du message)
  2. Appeler detect_phase_transition() sur le nouveau message
  3. Mettre à jour la phase avant tout autre traitement
  4. Court-circuiter le RAG si la phase est CLOSING
  5. Sérialiser l'état mis à jour dans la réponse pour persistance frontend
# Dans process_message(), après le chargement de l'historique :

conv_state = self._reconstruct_state(history)
new_phase = detect_phase_transition(conv_state.phase, message.content)
if new_phase:
    conv_state.phase = new_phase
    logger.info(f"[State] Phase transition → {new_phase.value}")

# Court-circuit RAG en phase CLOSING
if conv_state.phase == ConversationPhase.CLOSING:
    return await self._handle_closing_phase(message, conv_state, conversation_id, history)
Résultat attendu : Le chatbot ne relancera plus jamais un diagnostic en phase CLOSING. La cause racine confirmée est utilisée directement pour générer le message au dépositaire.

2 Stratégie de filtrage RAG (Retrieval Filtering Strategy)

2.1 Problème racine

L'orchestrateur actuel passe query=effective_query sans aucun filtre de domaine. Qdrant effectue une recherche de similarité vectorielle pure, qui peut ramener des chunks sur des incidents SEBA, 42C ou VLAN si ceux-ci ont une similarité cosinus marginalement plus élevée que des chunks sur les masques de fichiers ORRAHD.

2.2 Architecture de filtrage en 4 couches

Couche 1 — Classification du type d'incident (avant retrieval)

# Enrichir le ticket structuré avec un domaine fonctionnel
# À ajouter dans nlp/taxonomy.py

FUNCTIONAL_DOMAINS = {
    # Script / Fichier / Extraction
    "script_file_error":     ["masque", "nommage", "fichier", "extraction", "ORRAHD", "input file", "script"],
    # Équipements réseau
    "network_equipment":     ["DSLAM", "VLAN", "VP", "ONT", "OLT", "GPON", "port"],
    # Ressources logiques
    "logical_resources":     ["t_d_controlable_rscs", "compteur", "ressource logique", "SEBA", "42C"],
    # Gestion des commandes
    "order_management":      ["commande", "OT", "RDV", "planification", "WorkOrder"],
    # Provisioning / Activation
    "provisioning":          ["activation", "désactivation", "création", "ManageEquipment"],
}

def classify_functional_domain(query: str, structured_ticket: StructuredTicket) -> str:
    """Retourne le domaine fonctionnel dominant pour orienter le filtre RAG."""
    text = (query + " " + " ".join(structured_ticket.extracted_keywords or [])).lower()
    scores = {domain: sum(1 for kw in keywords if kw.lower() in text)
              for domain, keywords in FUNCTIONAL_DOMAINS.items()}
    best = max(scores, key=scores.get)
    return best if scores[best] > 0 else "general"

Couche 3 — Seuil de similarité sémantique adaptatif

# Dans orchestrator.py — post-filtrage par score de cosinus
SIMILARITY_THRESHOLDS = {
    "CLOSING":       None,    # Pas de RAG en phase clôture
    "DIAGNOSTIC":    0.55,    # Seuil permissif — on cherche large
    "INVESTIGATION": 0.65,    # Seuil modéré — on se rapproche de la cause
    "RESOLUTION":    0.70,    # Seuil strict — uniquement la procédure pertinente
}

def apply_similarity_threshold(results, phase: ConversationPhase) -> list:
    threshold = SIMILARITY_THRESHOLDS.get(phase.value.upper())
    if threshold is None:
        return []  # Pas de résultats RAG pour CLOSING
    return [r for r in results if r.score >= threshold]

3 Isolation du contexte d'incident

3.1 Le problème du "contexte contaminé"

Lorsque le RAG récupère des blocs de connaissance sur des systèmes non pertinents (SEBA, 42C, VLAN), ces blocs sont injectés dans le prompt LLM comme contexte. Le LLM, incapable de distinguer le pertinent du non-pertinent, utilise tout ce qu'il voit pour générer une réponse.

3.2 Mécanisme d'isolation : IncidentContextGuard

# Nouveau module : app/services/chatbot/incident_context_guard.py

import re
from typing import List, Dict, Optional

class IncidentContextGuard:
    """
    Filtre les blocs de contexte RAG pour n'injecter dans le prompt LLM
    que les blocs pertinents à l'incident en cours.
    """

    def __init__(self, state: "ConversationState"):
        self.state = state

    def filter_context_blocks(
        self, context_blocks: List[Dict]
    ) -> List[Dict]:
        """
        Filtre les blocs RAG selon 3 critères :
        1. Système : le bloc ne doit pas mentionner un système exclu
        2. Domaine : le bloc doit appartenir au domaine fonctionnel de l'incident
        3. Pertinence : le score de confiance doit être >= seuil de phase
        """
        filtered = []
        for block in context_blocks:
            content = block.get("content", "").lower()
            # Critère 1 : système exclu
            if any(sys.lower() in content for sys in self.state.excluded_systems):
                continue
            # Critère 2 : domaine — si locked_systems sont définis, le bloc doit les mentionner
            if self.state.locked_systems:
                mentions_relevant_system = any(
                    sys.lower() in content for sys in self.state.locked_systems
                )
                if not mentions_relevant_system and block.get("source_type") != "diagnostic_engine":
                    continue
            filtered.append(block)
        return filtered

    def extract_incident_systems(self, text: str) -> List[str]:
        """
        Extrait les noms de systèmes mentionnés dans le ticket initial.
        Ces systèmes deviennent le périmètre autorisé du RAG.
        """
        KNOWN_SYSTEMS = [
            "BRASIL", "ORRAHD", "SEBA", "42C", "ARTEMIS", "IPON",
            "ADELIA", "SCA", "ORCHESTRA", "NECTAR", "TIGRE",
        ]
        return [s for s in KNOWN_SYSTEMS if s.lower() in text.lower()]

    def build_system_exclusion_list(
        self, ticket_text: str, all_systems: List[str]
    ) -> List[str]:
        """
        Les systèmes NON mentionnés dans le ticket sont exclus du RAG.
        """
        mentioned = set(self.extract_incident_systems(ticket_text))
        return [s for s in all_systems if s not in mentioned]

# Après la récupération des blocs RAG (orch_result) :

4 Verrouillage de la cause racine (Root Cause Locking)

4.1 Problème

Une fois que l'ingénieur a confirmé la cause racine, le chatbot doit la traiter comme un fait établi et immuable. Toute nouvelle recherche RAG ou tout nouveau raisonnement LLM doit partir de cette cause, et non la remettre en question.

4.2 Détection de la confirmation de cause racine

# Dans chatbot_service.py — détection de confirmation

_ROOT_CAUSE_CONFIRMATION_PATTERNS = re.compile(
    r"(?:"
    r"la\s+cause\s+(racine\s+)?(est|[eé]tait|c'est|c'[eé]tait)"
    r"|la\s+cause\s+[eé]tait"
    r"|le\s+probl[eè]me\s+(vient|venait|est|[eé]tait)\s+(de|du|des|d'un|d'une)"
    r"|j'ai\s+(identifi[eé]|confirm[eé]|trouv[eé])\s+(que|la\s+cause)"
    r"|cause\s*:\s*.{5,}"
    r"|root\s+cause\s*:\s*.{5,}"
    r"|en\s+cause\s*:\s*.{5,}"
    r")",
    re.IGNORECASE,
)

def extract_root_cause(message: str) -> Optional[str]:
    """
    Extrait la cause racine d'un message utilisateur.
    Retourne le texte de la cause ou None.
    """
    m = _ROOT_CAUSE_CONFIRMATION_PATTERNS.search(message)
    if not m:
        return None
    # Extraire le texte après le pattern
    start = m.end()
    cause_text = message[start:start+300].strip().split("\n")[0].strip()
    return cause_text if len(cause_text) > 10 else message[:300]

4.3 Mécanisme de verrouillage dans l'état conversationnel

# Dans process_message(), avant toute autre logique :

# Si la cause racine est déjà verrouillée, ignorer tout RAG contradictoire

4.5 Comportement en phase CLOSING avec cause racine verrouillée

async def _handle_closing_phase(
    self,
    message: ChatMessage,
    state: ConversationState,
    conversation_id: str,
    history: List[Dict],
) -> ChatResponse:
    """
    Phase de clôture : génère le message de clôture sans appeler le RAG.
    Utilise uniquement l'état conversationnel et la cause racine verrouillée.
    """
    audience = state.audience  # "depositor" par défaut en phase closing

    closing_system_prompt = f"""
Tu es un ingénieur N3 senior d'Orange Telecom rédigeant un message de clôture de ticket support.

INCIDENT TRAITÉ :
- Application : {state.application or message.app_id}
- Cause racine confirmée : {state.confirmed_root_cause}
- Procédure appliquée : {state.confirmed_procedure_id or "procédure manuelle"}

AUDIENCE : {audience}

INSTRUCTIONS :
- Génère DEUX sections distinctes :
  SECTION 1 — Résumé technique N3 (pour les archives) :
    Format : Incident | Cause racine | Action effectuée | Résultat
  SECTION 2 — Message pour le dépositaire :
    Ton : professionnel, bienveillant, non-technique
    Contenu : confirmer la résolution, expliquer la cause simplement,
              donner le conseil préventif, remercier pour le signalement
- Ne génère AUCUN diagnostic. Ne mentionne AUCUN système non lié à l'incident.
- Réponds en français.
"""

    response_text = await self.llm.generate(
        prompt=f"Message de clôture demandé par l'ingénieur.\nCause confirmée : {state.confirmed_root_cause}",
        system_prompt=closing_system_prompt,
    )

    return ChatResponse(
        message=response_text,
        sources=[],
        suggestions=["Créer une FR préventive", "Notifier l'équipe de la résolution"],
        confidence=1.0,
        conversation_id=conversation_id,
        app_id=message.app_id,
        pipeline_mode="CLOSING",
        trust_score=100,
        trust_label="closing_confirmed",
        diagnostic_available=False,
    )
Résultat attendu : En phase CLOSING avec cause racine verrouillée, le RAG n'est jamais appelé. Le LLM ne peut pas halluciner de nouveaux systèmes ou hypothèses. La réponse est 100% basée sur le fait établi.

5 Génération de réponse selon le rôle (Role-Aware Response Generation)

5.1 Les trois audiences cibles

🔧 Ingénieur N3
Audience technique
  • Vocabulaire technique complet (codes erreur, procedure_id, FR)
  • Structure : diagnostic → cause → étapes numérotées → escalade
  • Références aux sources (snippet_id, cluster_id)
  • Ton direct et factuel
👥 Collègue support
Audience semi-technique
  • Vocabulaire technique modéré (acronymes expliqués)
  • Structure : contexte → symptôme → action recommandée
  • Ton collaboratif ("je recommande", "tu peux essayer")
  • Moins de détails techniques bas niveau
📬 Dépositaire (utilisateur non-technique)
Audience non-technique
  • Aucun jargon technique (pas de codes erreur, pas de FR, pas de table SQL)
  • Structure : confirmation de résolution → explication simple → conseil préventif → formule de courtoisie
  • Ton professionnel, bienveillant, rassurant
  • Phrases courtes, vocabulaire courant

5.2 Détecteur d'audience

    if _DEPOSITOR_INDICATORS.search(message) or phase == ConversationPhase.CLOSING:
        return "depositor"
    if _COLLEAGUE_INDICATORS.search(message):
        return "colleague"
    return "n3_engineer"

6 Style de réponse technique humanisé

6.1 Problème du ton robotique

Le template actuel (format_diagnostic_response()) produit des réponses de la forme :

🔍 Incident détecté : script_file_error
📦 Application : BRASIL
🔗 Systèmes liés : BRASIL, ORRAHD
📋 Procédure suggérée (Source : FR-0842, Confiance : 🟢 Haute confiance)
[Liste mécanique d'étapes sans contexte humain]

Ce format convient pour les diagnostics N3, mais est inadapté pour une communication avec un dépositaire ou pour les phases de résolution/clôture.

6.2 Directives de style par phase

PhaseCe qu'il faut éviterCe qu'il faut faire
DIAGNOSTIC Réponses vagues, hypothèses non sourcées, introduction de systèmes non cités Hypothèses numérotées avec score de confiance, questions de clarification ciblées
INVESTIGATION Répéter les hypothèses déjà explorées, ignorer les nouvelles informations fournies Confirmer ce que l'ingénieur vient de trouver, affiner le diagnostic, converger vers une cause
RESOLUTION Proposer plusieurs procédures contradictoires, omission des pré-requis Une seule procédure claire, étapes numérotées, pré-requis en amont, vérification finale
CLOSING Repartir en diagnostic, mentionner des systèmes non liés, ton froid et mécanique Confirmer la résolution, expliquer simplement, conseil préventif, ton chaleureux

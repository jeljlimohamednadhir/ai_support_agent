⚙️ 1. Analyse du Parseur NLP

✅ Points forts

  • Pipeline structuré en 4 couches : Preprocessor → Enricher → Taxonomy → DiagnosticBehavior
  • Glossaire domaine BRASIL de 45 abréviations (avp, nd, nro, dslam…)
  • Extraction multi-pattern d'erreurs : B4002, AVP-1300, ORA-xxxxx, 42C, codes 3-5 chiffres
  • Taxonomie riche : 80+ types d'incidents hiérarchisés (catégorie → type)
  • 14 familles d'intention reconnues avec priorité explicite (INTENT_PRIORITY)
  • Détection de langue FR/EN pour bilinguisme
  • Score de confiance composite (intent + entités + codes erreur + type incident)
  • Gestion Unicode : NFC + strip caractères de contrôle
  • Détection d'apostrophes Unicode U+2019 dans _DEPOSITOR_INDICATORS

⚠️ Points faibles identifiés

  • Encodage CSV latin-1 non normalisé : les messages bruts contiennent des séquences Ã©, Ã¨ (latin-1 interprété UTF-8). Le preprocessor ne corrige pas ces artéfacts.
  • 60% des tickets restent en confiance faible (<0.55) après enrichissement, ce qui déclenche un flag requires_human_review non utilisé.
  • 66% sans code erreur extrait : les messages informels ne contiennent pas de code structuré ("avp 1300 bloque la demande" non détecté sans le pattern AVP[-\s]?\d+).
  • 32% d'intentions inconnues : les tickets opérationnels courts ("merci de supprimer le routeur NBLIL701") ne matchent aucun pattern d'intention.
  • Dépendance aux mots-clés exacts : _classify_intent() compare des sous-chaînes exactes, sans tolérance aux fautes, variantes ou synonymes.
  • Absence de NER pour les ND : les numéros ND (ex. 0563741427) ne sont pas extraits en tant qu'entité nommée structurée.
  • Synonymes manquants : "rejouer" = re-lancer, "recréer" = supprimer+créer, "dégager" = libérer — non mappés dans le glossaire ni les intentions.
  • Pas de détection de composants DSLAM/carte/port dans les messages : patterns d'ID équipement trop génériques ([A-Z]{2,5}[A-Z0-9]{2,4}\d{3,6}).
🚨 Problème critique — Encodage CSV Les messages user_sig du CSV source sont en latin-1 non converti (ex : "le ND est supprimÃ© de BRASIL"). Le TextPreprocessor appelle unicodedata.normalize("NFC", text) mais ne décode pas les séquences d'encodage cassé. Résultat : les regex et le glossaire échouent sur ces tokens corrompus.
⚠️ Problème structurel — Intent par sous-chaînes L'algorithme _classify_intent() fait un simple if p in text_lower pour chaque mot-clé. Il ne gère pas : les fautes de frappe, les variantes morphologiques (supprimer/suppression/supprimé), ni les expressions multi-mots ("impossible de lancer" matche "lancer" et "impossible" séparément). Cela génère des scores multi-intent flottants.

🛠️ Recommandations d'amélioration du parseur

#AméliorationImpactEffortImplémentation
1 Décodage latin-1→UTF-8 au chargement CSV Critique Faible Ajouter dans ticket_structurer.load_csv() : df['user_sig'] = df['user_sig'].apply(lambda x: x.encode('latin-1').decode('utf-8', errors='replace') if isinstance(x, str) else x) — ou forcer encoding='latin-1' + errors='replace'
2 Pattern ND dans l'extracteur d'entités Critique Faible Ajouter dans ENTITY_PATTERNS["nd_number"] : r"\b(0[1-9]\d{8,9})\b" (numéro de nœud de distribution 10 chiffres)
3 Synonymes opérationnels dans TYPO_MAP Élevé Faible Ajouter : "rejouer": "relancer", "recréer": "supprimer créer", "dégager": "libérer", "régulariser": "corriger", "rejeu": "relancer"
4 Intent basé sur TF-IDF ou embeddings Élevé Moyen Remplacer _classify_intent() par une classification vectorielle sur les clusters existants — utiliser les embeddings Qdrant déjà calculés pour classer l'intent par cosine similarity
5 Corriger detection_confidence du flag requires_human_review Élevé Faible Le flag est calculé mais n'est jamais utilisé dans le pipeline RAG. Brancher sur un workflow de validation (ex : JIRA label, Slack notif) ou au moins dans le log de chatbot
6 Détecter le type d'action BRASIL dans la taxonomie Élevé Moyen Créer un extracteur d'action composite : verbe + objet (ex. "supprimer + DSLAM" → deletion_request.dslam). Cela permettrait de sélectionner directement FR 189 pour "supprimer DSLAM impossible"
7 Normaliser les codes AVP en entités structurées Élevé Faible Le pattern r"\bAVP[-\s]?\d+\b" existe dans l'extracteur mais ne capture pas "avp 1300" en minuscules. Ajouter re.IGNORECASE systématiquement
8 Détecter les pièces jointes référencées Moyen Faible Beaucoup de messages mentionnent "Ci-joint la capture d'écran" sans que le parser ne note l'absence d'attachement analysable — ajouter un flag has_attachment_ref

Exemple concret — Ticket mal parsé

# ─── Message brut (CSV, encodage cassé) ───────────────────────────────────
"Bonjour. 4002 Erreur interne Brasil : merci de traiter l.AVP"

# ─── Problèmes d'extraction actuels ───────────────────────────────────────
preprocessed_text  → "4002 Erreur interne brasil : merci de traiter l.AVP"
                      (le "." vient de l'encodage latin-1 de l'apostrophe)
error_codes        → ["4002"]        ✅ OK
intent             → "investigate_error"  ⚠️  mais "avp" → pas de pattern AVP
entities           → [("error_code", "4002")]
incident_type      → "backend_error.api_error"  ⚠️  devrait être "command_failure.avp_constraint"
trust_score        → 0.30  ← trop bas car pas de code AVP extrait

# ─── Avec les corrections proposées ──────────────────────────────────────
1. Décodage latin-1 → "l'AVP" (apostrophe correcte)
2. Pattern AVP (case-insensitive) → error_code = ["4002", "AVP"]
3. Synonyme "traiter" → action = "correct" → incident_type = "command_failure.avp_constraint"
4. trust_score → 0.40 (code AVP reconnu → bonus +0.15 → meilleure sélection FR)
🗄️ 2. Analyse de la Qualité des Données

2.1 — Source tickets.csv (222 tickets structurés)

✅ Forces

  • Dataset réel de production (INC001010…)
  • Champs riches : inc_resume, user_sig, inc_solution, inc_cause, datetime_debut/resolution, groupes N2/N3
  • Données de résolution disponibles (inc_solution) utilisables pour le clustering supervisé
  • Traçabilité multi-système : application_ticket, application_ticket_resolution

❌ Lacunes & Problèmes

  • Encodage cassé : latin-1 dans un fichier UTF-8 → artéfacts Ã©, Ã¨, Ã omniprésents dans user_sig
  • Solutions très courtes : "ras bdd brasil", "La commande est débloquée", "le ND est supprimé" — pas exploitables seules pour une FR
  • Champ user_sig absent dans 47 tickets (null ou "-") — le parseur utilise alors inc_resume qui est moins riche
  • Pas de lien direct vers une FR dans les champs CSV — impossible de valider automatiquement "ce ticket a été résolu par FR 130"
  • Période courte : décembre 2025–mars 2026 seulement — biais saisonnier possible, incidents rares sous-représentés

✅ Forces

  • 30 fichiers sources issus de composants réels : connectorCL, brasil-api, sollicitationDLM, sollicitationFTTH…
  • Tous les événements sont de niveau ERROR → signal/bruit excellent
  • 100% des events ont un timestamp exploitable
  • Patterns récurrents bien capturés : DSLAM_CLOSED (33×), DUPLICATE_RESOURCE (129×), TRANSACTION_KO (38×), DB_DEADLOCK (27×)

❌ Lacunes & Problèmes

  • 0% d'events avec user_id — impossible de corréler un log avec un ticket ou un utilisateur
  • 18% seulement ont un code erreur structuré — les 82% restants ont des messages en texte libre non normalisé

🤖 3. Impact potentiel sur le Chatbot

🔴 Types d'erreurs générables

  • Hallucination de procédures : face à un ticket "1300" dont FR 130 est vide (89 mots), le LLM remplira les lacunes avec des procédures génériques inventées ou issues d'autres domaines
  • Recommandation de mauvaise FR : si le cluster 1300 pointe vers le mauvais chunk RAG (faute de lien cluster→FR), la FR 136 ou 194 peut être suggérée à tort
  • Perte d'information sur le ND : le numéro de nœud de distribution (clé primaire du problème) n'est pas extrait → le chatbot ne peut pas vérifier l'état du ND, ni l'inclure dans le message de clôture
  • Intent incorrect sur messages courts : "merci de supprimer le routeur NBLIL701" → intent=unknown → contexte générique fourni → réponse hors sujet
  • Artéfacts d'encodage dans les réponses : si les tickets mal encodés sont injectés comme contexte RAG, le LLM peut reproduire les artéfacts (Ã©) dans ses réponses

🟡 Risques pour la résolution

  • Faible discriminance du vecteur d'embedding pour les clusters "2025_unknown" qui regroupent des tickets très différents (B4002 sur SEBA, B4002 sur IPON, B4002 sur creation de VLAN) — le RAG ramènera du bruit
  • Trust gate trop restrictif : avec trust_score moyen à 0.33 pour les tickets et 0.36 pour les records log, de nombreuses réponses légitimes seraient bloquées par le seuil de confiance
  • Absence de corrélation ticket ↔ log : le chatbot ne peut pas enrichir une réponse avec "à ce moment, les logs montrent l'erreur DSLAM_CLOSED" car le lien temporel n'est pas construit
  • Escalade trop tardive : sur les 72 tickets "unknown", le chatbot produit des réponses génériques au lieu d'escalader immédiatement vers un expert
  • Réponses de clôture incomplètes : sans ND extrait et sans lien FR→solution, les messages de clôture générés manqueront les éléments essentiels (référence de la correction, numéros de ressources affectées)

Chatbot Reference — AI Support Agent (N3)
=========================================

1) Objectif
-----------
Ce document est destiné aux ingénieurs N3 en production. Il décrit les capacités du chatbot, les signaux de confiance à vérifier et les méthodes pour extraire des informations techniques fiables (tables, FR, tickets) sans exécuter d'actions depuis le chatbot.


2) Intents principaux & routage
-------------------------------
- diagnostic_request : erreurs/code/plantage (RAG + historique)
- procedure_lookup : récupération FR/procédure (KB-first)
- root_cause_exploration : consolidation d'indices (tickets/procédures)
- log_investigation : orientation sur quelles traces analyser
- ticket_summary / ticket_closing : synthèse et message pour Jira
- find_jira / explain_jira : recherche par texte OU clé issue (pattern [A-Z]+-\d+)
- explain_data_model : explication structurée du schéma BRASIL (tables/PK/FK/colonnes)
- knowledge_gap_detection : fallback indiquant l'absence de FR


3) Cas d'usage N3 (exemples)
----------------------------
Table — explicitation (ex : t_ports)
- Requête type :
  Explique la table t_ports : PK, colonnes importantes (types), FK sortantes et tables qui la référencent. Cite les sources (snippet_id / procedure_id).
- Réponse attendue : vue synthétique, PK, colonnes critiques, FK sortantes, FK entrantes, liste des sources exactes.

Jira — reformulation technique
- Requête type :
  Explique JIRA BRASIL-10861 en 4 points : contexte | symptôme | actions exécutées | prochaines étapes (techniques)

Remarque : le chatbot effectue un lookup direct quand une clé est fournie (JQL key = "..."), puis peut demander au LLM de reformuler.


4) Signaux de fiabilité (checklist rapide)
----------------------------------------
- Sources : vérifier la présence de <snippet_id>, <procedure_id> ou lien Jira.
- Trust score / label : préférez les réponses avec trust élevé (ex: >=80) pour prise d'action.
- Context blocks : vérifier que les context_blocks renvoyés correspondent aux FR/tickets cités.
- Prior_procedure_id : si présent, la procédure doit être réutilisée — pas d'invention.
- Absence de sources : traiter la réponse comme hypothétique et documenter la connaissance manquante.


5) Comment formuler les demandes (pratiques)
-------------------------------------------
1. Nommez explicitement l'entité (ex : t_ports, BRASIL-10861).
2. Demandez le format exact (liste, tableau, étapes numérotées).
3. Exigez la liste des sources (snippet_id / procedure_id / lien Jira).
4. Pour les procédures : demandez étapes numérotées + identifiant FR.

Exemples utiles :
- "Liste les colonnes de t_ports avec types et PK"
- "Pour BRASIL-10861, résume en 4 points techniques"


6) Règles opératoires en prod
-----------------------------
- Le chatbot RESTE en lecture : aucune exécution de commande ou test n'est initiée via le chatbot.
- Toute action corrective doit reposer sur une FR existante et une revue humaine.
- Pour capturer un manque de connaissance, créez une FR et joignez le snippet_id/context renvoyé.
- Les extractions de données / exécutions SQL se font via pipelines OPs dédiés, hors chatbot.


7) Prompt et format recommandés (N3)
----------------------------------
Table (extraction complète) :
Explique la table t_ports : (1) rôle & contexte ; (2) PK ; (3) colonnes critiques (type) ; (4) FK sortantes & entrantes ; (5) sources (snippet_id/FR).

Jira (reformulation N3) :
Pour BRASIL-10861, rédige en 4 points techniques : Contexte | Symptôme | Actions effectuées (logs/commandes citées) | Prochaines étapes.


8) Limitations & recommandations
--------------------------------
- Ne pas considérer une réponse sans sources comme fiable pour exécution.
- Préférez les réponses avec trust score élevé et sources identifiables.
- Documentez toujours le contexte (snippet_id/proc_id) pour audit et injection KB ultérieure.

Diagnostic du parseur actuel

Le parseur actuel est basé sur des regex et des comparaisons de sous-chaînes exactes. Cette architecture produit de faux négatifs à grande échelle sur des messages opérationnels courts, informels ou mal encodés — les 3 caractéristiques dominantes des tickets BRASIL N3.

🔴 Problème #1 — Encodage cassé (mojibake)

Le CSV tickets.csv est en latin-1, ouvert en UTF-8. Les accents français deviennent des séquences Ã©, Ã¨. Le preprocessor actuel fait un unicodedata.normalize("NFC", text) mais ne décode pas ces séquences. Résultat : 60%+ des tokens sont corrompus avant d'entrer dans le pipeline NLP.

# Input CSV réel :
"nd supprimÃ© de brasil"
# Attendu :
"nd supprimé de brasil"
# Impact : le mot "supprimé" n'est pas reconnu → intent UNKNOWN

🔴 Problème #2 — Intent par sous-chaîne exacte

La méthode _classify_intent() teste if p in text_lower pour chaque mot-clé. Elle ne gère pas les synonymes, variantes morphologiques, ni les phrases multi-mots. Un message comme "rejouer la commande" ne matche pas "relancer", et reste unknown.

# Actuel (vulnérable aux synonymes) :
if "relancer" in text_lower:
    intent = "launch_command"
# "rejouer", "repasser", "forcer" → intent = UNKNOWN

⚠️ Problème #3 — Entités télécom non extraites

Les entités critiques N3 — ND (numéro à 10 chiffres), NRO (identifiant équipement), PORT/SLOT/CARD — ne sont pas extraites en entités structurées. Un ticket "erreur sur port 24 du DSLAM-LIL701-01" perd toutes les informations de localisation de la panne.

⚠️ Problème #4 — Faux positifs codes erreur

Le pattern \b\d{3,5}\b extrait les années 2024, 2025 comme codes erreur. Dans les 51 FR, les top "codes" extraits sont : 2024 (×28), 2016 (×14), 2017 (×10) — tous des années dans les textes des fiches, pas des codes BRASIL réels.

🟠 Problème #5 — 0/20 clusters liés à une FR

Le champ suggested_procedure_ids est vide pour tous les clusters. Le pipeline d'indexation RAG ne peut donc pas passer du cluster identifié à la FR correspondante — il doit s'en remettre uniquement à la recherche vectorielle, qui échoue quand les embeddings ne discriminent pas assez.

🟠 Problème #6 — Flag requires_human_review mort

Le flag est calculé (confidence < 0.55) mais jamais branché sur aucun workflow. Dans le dataset analysé : 133/222 tickets devraient être flaggés, zéro l'est réellement dans le pipeline de sortie.

Architecture du Smart N3 Parser

Le Smart N3 Parser est un pipeline modulaire à 7 étapes. Chaque étape est une classe indépendante et testable. Le parseur produit un objet IncidentContext qui contient tout le contexte structuré nécessaire pour le RAG et le LLM.

1

EncodingNormalizer — Correction d'encodage

Détecte et corrige automatiquement le mojibake latin-1/UTF-8. Applique une table de substitution de 25+ séquences corrompues (Ã©→é, Ã¨→è…). Tente ensuite un round-trip byte-level. Retourne un flag encoding_fixed=True pour traçabilité.

"supprimÃ©" → "supprimé" ✅

↓
2

TextNormalizer — Normalisation télécom

Strip le bruit de politesse (bonjour, merci, svp…). Applique le dictionnaire de synonymes opérationnels BRASIL (50+ entrées). Normalise les espaces et sauts de ligne. Expansion des abréviations pour l'embedding (nd → nœud de distribution).

"rejouer la commande sur le nd svp" → "relancer la commande sur le nd"

↓
3

TelecomEntityExtractor — NER télécom

Extrait 13 types d'entités : ND, NRO, DSLAM, AVP, PORT, SLOT, CARD, EQUIPMENT, ORDER_ID, USER_ID, IP_ADDRESS, VLAN_ID, TRANSACTION_ID. Chaque entité a un score de confiance. Déduplique par (type, valeur canonique) en gardant la confiance la plus haute.

"DSLAM-LIL701-01 port 24" → DSLAM: LIL701-01, PORT: 24

↓
4

ErrorCodeDetector — Détection codes erreur

15 patterns de détection ordonnés par spécificité. Filtre les années (2024, 2025) par regex d'exclusion. Associe chaque code à sa famille (BRASIL, AVP, ORACLE, GENERIC). Retourne une liste triée par confiance décroissante.

"avp 1300 erreur 4002" → [AVP1300 (BRASIL, conf=0.99), 4002 (BRASIL, conf=0.92)]

↓
5

IntentClassifier — Classification sémantique

Scoring pondéré sur 17 catégories d'intent. Chaque intent a des groupes de phrases avec des poids différents. L'intent gagnant est sélectionné par priorité (INTENT_PRIORITY, 0-100) puis par score. Stub d'embedding cosine similarity disponible pour migration Phase 2.

"commande bloquée avp 1300" → ORDER_BLOCKED (conf=0.82)

↓
6

ConfidenceScorer — Calcul de confiance composite

Formule composite : intent_conf×0.40 + code_erreur×0.20 + entité_ND/NRO×0.15 + système_connu×0.10 + entités_multiples×0.10 + longueur_message×0.05. Plus complétude : ND×0.30 + code_erreur×0.30 + système×0.20 + action×0.20.

↓
7

RAGQueryBuilder — Génération requêtes Qdrant

Construit deux requêtes : primary (intent + code + ND + NRO + texte normalisé 20 mots) et fallback (intent + système + BRASIL). Fournit directement les FR suggérées via table _FR_LOOKUP (code erreur → IDs de FR).

Primary: "order blocked erreur 1300 ND 0563741427 NRO LIL701"

Détection d'intention

🔵 Catalogue d'intents (17 catégories)

Chaque intent est défini par des groupes de phrases avec des poids : les phrases précises ont un poids 1.0–1.3, les phrases ambiguës 0.5–0.8. L'intent gagnant est sélectionné par priorité absolue (0-100) plutôt que par score seul, évitant les victoires de mots-clés génériques.

Implémentation Python

Le module complet est dans backend/app/services/nlp/smart_n3_parser.py. Voici les extraits clés de chaque classe.

Step 1 — EncodingNormalizer

class EncodingNormalizer:
    """Détecte et corrige le mojibake latin-1/UTF-8 automatiquement."""

    _MOJIBAKE_MAP: Dict[str, str] = {
        "Ã©": "é", "Ã¨": "è", "Ã ": "à", "Ã®": "î",
        "Ã§": "ç", "Ã‰": "É", "â€™": "'",  # apostrophe courbe
        # ... 25 entrées supplémentaires
    }

    def normalize(self, text: str) -> Tuple[str, bool]:
        # 1. Substitution des séquences mojibake connues
        if _LATIN1_CORRUPTION.search(text):
            text = self._MOJIBAKE_RE.sub(
                lambda m: self._MOJIBAKE_MAP[m.group(0)], text
            )
            fixed = True

        # 2. Round-trip byte-level pour cas non couverts
        try:
            probe = text.encode("latin-1").decode("utf-8")
            if probe != text and self._looks_valid_french(probe):
                text, fixed = probe, True
        except (UnicodeEncodeError, UnicodeDecodeError):
            pass

        # 3. NFC + strip caractères de contrôle
        text = unicodedata.normalize("NFC", text)
        text = "".join(c for c in text if unicodedata.category(c)[0] != "C")
        return text, fixed

Step 3 — TelecomEntityExtractor

class TelecomEntityExtractor:
    def extract(self, text: str) -> List[TelecomEntity]:
        entities = []
        for entity_type, patterns in TELECOM_ENTITY_PATTERNS.items():
            for pattern, conf in patterns:
                for m in re.finditer(pattern, text, re.IGNORECASE):
                    try:
                        raw_val = m.group(1)
                    except IndexError:
                        raw_val = m.group(0)
                    if not raw_val or len(raw_val.strip()) < 2:
                        continue
                    canonical = self._canonicalize(entity_type, raw_val.strip())
                    entities.append(TelecomEntity(
                        entity_type=entity_type, value=canonical,
                        raw_value=m.group(0), confidence=conf,
                        start=m.start(), end=m.end(),
                    ))
        return self._deduplicate(entities)

Step 4 — ErrorCodeDetector (avec filtrage années)

_YEAR_EXCLUSION = re.compile(r"^(19|20)\d{2}$")

class ErrorCodeDetector:
    def detect(self, text: str) -> List[ErrorCode]:
        codes, seen = [], set()
        for pattern, prefix, conf in ERROR_CODE_PATTERNS:
            for m in re.finditer(pattern, text, re.IGNORECASE):
                raw_code = m.group(1) if m.lastindex else m.group(0)
                canonical = (prefix + raw_code).upper().replace(" ", "")
                if _YEAR_EXCLUSION.match(canonical):  # ← filtre 2024, 2025…
                    continue
                if canonical not in seen:
                    seen.add(canonical)
                    codes.append(ErrorCode(raw=m.group(0), canonical=canonical,
                                              code_type=self._CODE_FAMILY.get(canonical, "GENERIC"),
                                              confidence=conf))
        return sorted(codes, key=lambda c: c.confidence, reverse=True)

Step 5 — IntentClassifier (scoring pondéré + priorité)

class IntentClassifier:
    def classify(self, text: str) -> Tuple[Intent, float]:
        text_lower = text.lower()
        scores: Dict[Intent, float] = {}

        for intent, phrase_groups in INTENT_PROFILES.items():
            total = 0.0
            for phrases, weight in phrase_groups:
                for phrase in phrases:
                    if phrase in text_lower:
                        total += weight
            if total > 0:
                scores[intent] = total

        if not scores:
            return Intent.UNKNOWN, 0.20

        # Sélection par priorité absolue, puis score comme départage
        best = max(
            scores.keys(),
            key=lambda i: (INTENT_PRIORITY.get(i, 0), scores[i])
        )
        confidence = min(0.40 + scores[best] * 0.12, 0.97)
        return best, round(confidence, 3)

Normaliseur d'incidents

L'IncidentNormalizer est la couche d'intégration entre le Smart N3 Parser et le reste du pipeline (RAG, LLM, chatbot). Il sérialise l'IncidentContext dans un format plat prêt pour Qdrant et le prompt builder. 

# Utilisation : normaliser un ticket CSV ou un message chatbot
from app.services.nlp.smart_n3_parser import incident_normalizer

# ── Message unique ───────────────────────────────────────────────────────

    raw_message="nd supprimÃ© par erreur brasil ND 0563741427",
    ticket_id="INC001010426752"
)
print(result["intent"])          # → "DELETE_RESOURCE"
print(result["nd_number"])       # → "0563741427"
print(result["encoding_fixed"])  # → True
print(result["suggested_fr_ids"]) # → []  (pas de code erreur ici)

# ── Batch CSV ────────────────────────────────────────────────────────────

    {"ticket_id": "INC001", "raw_text": "avp 1300 bloque commande NRO LIL701"},
    {"ticket_id": "INC002", "raw_text": "impossible creer routeur erreur B4002"},

for r in results:
    print(f"{r['ticket_id']}: {r['intent']} → {r['suggested_fr_ids']}")

✅ Impact du dictionnaire sur le clustering En normalisant ces synonymes avant l'embedding, les tickets "rejeu de la commande sur ND 0563741427" et "relancer la commande sur ND 0634581234" tombent dans le même cluster sémantique.

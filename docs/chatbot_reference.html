Référence Chatbot — AI Support Agent N3

Référence technique complète (mars 2026) — pipelines actifs, intentions reconnues, couche NLP, trust gate, moteur diagnostic, mémoire conversationnelle et prompts opérationnels.

1) Objectif de ce document

Référence technique destinée aux ingénieurs N3 en production. Elle décrit le comportement réel du service ChatbotService (1 161 lignes, mars 2026) : pipelines actifs, intentions reconnues, couche NLP diagnostique, trust gate, moteur diagnostic N3, mémoire conversationnelle, reformulation de requêtes, intégration Jira, analyse ML, et inférence technique.

Architecture : Le chatbot délègue systématiquement la recherche de connaissance à l'IntelligenceOrchestrator, qui sélectionne le pipeline adapté au profil de l'application. Le LLM n'est appelé qu'après résolution du contexte structuré.

3) Cas d'usage opérationnels (N3)

3.1 Diagnostic d'incident (flux principal)

Impossible de supprimer le DSLAM280, erreur B4002 lors de l'appel ManageEquipmentService. Les logs montrent un timeout sur la passerelle.

Flux effectif : reformulation de requête (si follow-up) → orchestrateur → NLP enrichment (type incident, slots) → trust gate → DiagnosticEngine (log patterns + procédures) → LLM avec context enrichi. Réponse attendue : cause racine probable, procédure FR, étapes ordonnées.

3.2 Explication d'un symbole technique

C'est quoi ManageTechnicalConfigurationService ?
À quoi sert OrderProcessor ?

Le service détecte l'intention tech_inference via regex CamelCase/snake_case. Le LLM raisonne à partir du nom, des conventions de nommage et du contexte applicatif. Réponse structurée en 3 parties : (1) certitudes, (2) inférences, (3) incertitudes. Le trust gate est bypassé — l'incertitude est exprimée dans la réponse.

3.3 Explication d'une carte Jira

Explique BRASIL-10861 en 4 points : contexte | symptôme | actions exécutées | prochaines étapes

Lookup JQL direct key = "BRASIL-10861" → reformulation LLM N3. Si aucune clé dans le message mais qu'une clé est présente dans l'historique de la conversation, elle est réutilisée automatiquement. Vérifier systématiquement la section sources.

3.4 Recherche Jira par mots-clés

Y a-t-il des tickets Jira sur la suppression DSLAM ?

JQL full-text project = BRASIL AND text ~ "..." ORDER BY updated DESC (max 5 résultats). Retourne liste formatée avec statut, priorité, assigné, lien direct.

3.5 Analyse ML des tickets

Quelles sont les causes principales des tickets BRASIL cette semaine ?
Donne-moi le MTTR moyen et les anomalies temporelles.

Appel live à l'exec-summary du module Classification ML (si données uploadées). Fallback sur ml_insight Qdrant. Réponse : volume, MTTR médian, top causes, scores de criticité, anomalies temporelles, recommandations prioritaires.

3.6 Explication du schéma de données

Explique la table t_ports : PK, colonnes importantes (types), FK sortantes et tables qui la référencent. Cite les sources (snippet_id / procedure_id).

Routé via le pipeline RAG standard. La réponse doit contenir PK, colonnes critiques avec types, FK out, FK in, et les snippet_id des sources utilisées.

4) Couche NLP, Trust Gate & Signaux de fiabilité

4.1 Couche NLP diagnostique (anti-hallucination)

Activée si le module app.services.nlp.diagnostic_behavior est disponible. Elle fournit :

  • ticket_enricher — enrichit la requête brute en ticket structuré : type d'incident, confiance, slots extraits.
  • slot_filler — détecte les slots manquants (équipement, code erreur, action) et génère une question de clarification si nécessaire.
  • diagnostic_reasoner — construit le system prompt enrichi et vérifie le trust gate.
  • Mémoire de procédure — extrait prior_procedure_id de l'historique pour éviter toute contradiction inter-tour.

4.2 Trust Gate (seuil 40/100)

Avant l'appel LLM, si le score de confiance de l'orchestrateur est < 40 ET qu'aucun context_block n'est disponible, le chatbot émet un refus gracieux formaté (trust_label: insufficient) sans appeler le LLM. Les cas suivants bypassent le gate :

  • Questions de suivi conversationnel (reformulation implicite)
  • Intents contextuels : summarize, ticket-message, logs
  • tech_inference (le LLM signale lui-même l'incertitude)

4.4 Autres signaux à contrôler

  • sources[] — chaque source contient name, type, content_snippet, relevance (0–1). Vérifier que les procedure_id / snippet_id correspondent aux FR citées.
  • context_blocks — blocs de connaissance injectés dans le prompt. Si le DiagnosticEngine est actif, son bloc est inséré en premier avec source_type: diagnostic_engine.
  • diagnostic_available — booléen indiquant si le moteur diagnostic a produit une procédure exploitable.
  • procedure_id / exceptions_detected — présents quand le DiagnosticEngine a identifié une procédure N3 et des exceptions correspondantes.

5) Mémoire conversationnelle & reformulation de requêtes

5.1 Chargement de l'historique

Le service charge jusqu'à 8 messages (4 échanges) par conversation. Priorité :

  1. Historique fourni directement par le frontend (conversation_history) — 8 messages max
  2. Chargement depuis la base de données via conversation_id (entier) si la priorité 1 est absente

5.2 Reformulation automatique (follow-up)

Si la question déclenche les followup patterns (ex : commence par « et », « mais », « pourquoi »; contient « ce problème », « cela », « y a-t-il »…), le service :

  1. Concatène les 6 derniers messages en texte
  2. Demande au LLM une reformulation autonome (max 20 mots, max 60 tokens)
  3. Utilise la reformulation pour la recherche vectorielle — la question originale est conservée pour la réponse
Note : Si la reformulation dépasse 200 caractères ou échoue, la question originale est utilisée directement.

5.3 Résumé de contexte (_build_context_summary)

Les entités techniques de l'historique (DSLAM, VLAN, ONT, codes FR, codes erreur, actions…) sont extraites et injectées dans le system_prompt en ~20 tokens. Exemple :

Contexte de la conversation en cours : suppression DSLAM280, FR:189, erreur impossible

5.4 Extraction des sources — bonne pratique

  1. Toujours copier les snippet_id / procedure_id renvoyés dans sources[] pour audit.
  2. Pour les tables : demander explicitement PK / colonnes importantes / FK out / FK in.
  3. Pour les procédures : exiger l'identifiant FR et les étapes numérotées.
  4. Pour les tickets Jira : fournir la clé complète (BRASIL-XXXXX) pour un lookup direct.

6) Moteur Diagnostic N3 (DiagnosticEngine)

Activé si le module app.services.diagnostic.diagnostic_engine est disponible. Il s'exécute avant l'appel LLM, en parallèle du pipeline RAG standard.

  • Analyse query, logs, stack_trace pour identifier des exceptions connues et des patterns de logs.
  • Retourne une procédure N3 (procedure_id, procedure_title, trust_score, context_text, exceptions_matched).
  • Si exploitable (is_usable()), son bloc est injecté en premier dans context_blocks avec source_type: diagnostic_engine, prioritaire sur les blocs RAG.
  • Sa llm_instruction override les instructions LLM standard — assure la cohérence procédure ↔ réponse.
Bonnes pratiques : Pour déclencher le DiagnosticEngine au maximum, fournir le stack trace et les logs dans les champs dédiés (pas uniquement dans le texte libre). Le champ diagnostic_available de la réponse confirme si une procédure a été identifiée.

7) Règles opératoires en production

  • Ne pas exécuter de commandes ou tests depuis le chatbot : lecture et récupération de connaissances uniquement.
  • Valider toute action corrective par une procédure FR existante et par revue humaine avant exécution.
  • Si trust_label: insufficient est retourné, créer une FR et noter le contexte précis pour injection KB ultérieure.
  • Pour extraire des données ou exécuter des requêtes SQL, suivre la procédure interne OPs (hors chatbot).
  • Si prior_procedure_id est présent dans un tour, le chatbot doit maintenir la cohérence avec cette procédure — signaler toute contradiction observée.
  • La validation N3 est déclenchée automatiquement (ValidationService.create_chatbot_task) pour chaque réponse avec DB active — les tâches sont visibles dans le module de validation.

8) Prompts opérationnels (exemples N3)

Diagnostic d'incident

Impossible de supprimer le DSLAM280 sur BRASIL. Erreur B4002, timeout passerelle. Logs : [java.net.SocketTimeoutException: connect timed out]. Quelle est la cause racine et la procédure de résolution ?

Schéma de données

Explique la table t_ports en donnant : (1) rôle et contexte ; (2) PK ; (3) colonnes critiques avec types ; (4) FK sortantes et FK entrantes ; (5) sources (snippet_id / FR).

Jira — reformulation N3

Pour BRASIL-10861, rédige en 4 points pour N3 : Contexte technique | Symptôme observé | Actions déjà menées (préciser logs/commandes citées) | Prochaines étapes recommandées.

Inférence technique

C'est quoi ManageTechnicalConfigurationService ? Donne ce que tu sais avec certitude, ce que tu peux inférer, et ce qui reste incertain.

Analyse ML

Quelles sont les causes principales des incidents BRASIL ce mois-ci ? Donne le MTTR médian, les anomalies temporelles et les 3 recommandations prioritaires.

Suivi conversationnel

Après un premier diagnostic, des questions de suivi comme « et pourquoi ça timeout sur la passerelle ? » ou « y a-t-il une carte Jira pour ce problème ? » sont reformulées automatiquement. Pas besoin de répéter le contexte complet.

9) Limitations & recommandations

  • Le chatbot ne remplace pas les procédures d'exploitation — il sert d'aide à la décision et de synthèse documentaire.
  • Toujours joindre les sources (snippet_id, procedure_id, lien Jira) pour audit avant toute action corrective.
  • Pour requêtes SQL ou extraction de données en production, utiliser les pipelines OPs autorisés avec revue humaine.
  • Si la couche NLP (_NLP_AVAILABLE = False) ou le DiagnosticEngine (_DIAGNOSTIC_ENGINE_AVAILABLE = False) sont inactifs, le chatbot fonctionne en mode dégradé — les diagnostics sont moins précis et le trust gate est désactivé.
  • La recherche Jira est limitée au projet BRASIL (JQL hardcodé). Pour d'autres projets, la recherche full-text ne s'applique pas.
  • Le module ML Analysis nécessite un CSV uploadé et un modèle entraîné dans le module Classification ML — sans cela, la réponse est trust_label: no_data.
À ne jamais faire : Se baser sur une réponse avec trust_label: insufficient ou trust_score: 0 pour une action corrective en production. Créer une FR et escalader.
